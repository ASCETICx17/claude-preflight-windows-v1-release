# DNS / WebRTC：代码怎样运行，为什么反复出现未知

这两项可以实现，但它们是观测工具。程序能修正等待、解析和结果判定；不能让一条不通的 DNS 或 UDP 路径凭空收到回复。当前两项均为黄色提醒，不参与启动放行。

## DNS 不是“请求网页后抄 IP”

实现位于 [LeakChecks.ps1](../windows/local/LeakChecks.ps1)，入口 Invoke-CSDnsLeakCheck。

```text
经保存的 HTTP 代理向 bash.ws 申请本轮 ID
    ↓
六个随机域名 → Windows Resolve-DnsName（并发）
    ↓                      ↓
Windows 当前 DNS 路径       记录成功 / 系统错误 / 程序停止等待
    ↓
远端权威服务器记录：哪些递归 DNS 服务器来问过这些域名
    ↓
经同一 HTTP 代理下载本轮 JSON 报告
    ↓
有效报告 → 显示 DNS 服务器地址 → 自动填入首次草稿 → 可选基线比较
```

会话和报告通过 HTTPS 接口；中间的六次查询由 Windows 执行。网页接口 HTTP 200 只说明报告接口能访问，不能保证中间 DNS 查询成功。浏览器网页可能使用独立 DoH，和 Windows 当前解析路径不同。

保存的 DNS 列表只是历史比较样本。它不会设置系统 DNS，不会让服务器开始回答，也不改变代理。即使保存了十几个地址，本轮没有有效报告仍然无法比较。现在会显示“已保存比较基线 N 个；本轮尚未比较”。

## WebRTC 不请求 Claude

实现由 [BrowserProbe.cs](../windows/local/probes/BrowserProbe.cs) 和 [webrtc.js](../windows/local/probes/webrtc.js) 共同完成。

```text
独立临时 Edge → 加载项目本地 HTML / JS
    ↓
并发创建两处 STUN 的 RTCPeerConnection
    ↓
浏览器按当前网络发送 UDP → Google / Cloudflare STUN
    ↓
返回 ICE 候选与错误 → 本机调试通道回传 → 核对地址
```

HTTP 代理参数不能保证 UDP 跟着走代理。程序先经代理解析 STUN 名称，增加 IPv4 备用地址，但这只能帮助找到服务器，不能替 UDP 修路。没有读取 Claude 账号、对话或内部浏览器状态。

网页中 HTTP 出口显示正常、WebRTC 公网地址为空，有的网站也会标绿色“无泄露”。本工具将其表述为“本轮没有观察到暴露，但未验证 UDP 出口”，保持黄色。两者对空结果的评价不同，不能把网页绿色等同于收到 STUN 回复。

## 前几版反复失败的原因

| 层面 | 已知问题 / 证据 | 应怎样解决 |
|---|---|---|
| 报告解析 | 早期没有正确区分服务的 error 对象、格式变化与有效报告，导致 HTTP 200 也被笼统报成结构错误 | 客户端分类解析已修；当前错误不能都归因于 JSON |
| 等待预算 | v9 虽有 30 秒总时限，DNS 子阶段仍最多 10 秒、ICE 初次最多 16 秒；程序截止与系统超时曾混淆 | v9.1 使用剩余预算，并显示实际等待、分配上限及错误来源 |
| 浏览器启动 | 浏览器启动耗时可能挤掉 ICE 返回结果的时间 | v9.1 从总预算扣除启动 / 页面加载时间，通过绝对截止时间约束 JS |
| TUN DNS 路径 | 前次故障环境中，TCP DNS 在回复前断开；同代理的标准 HTTPS DoH 返回成功；另一次 Windows 查询约 11.65 秒自行返回 1460 | 优先人工把 TUN 远端 DNS 改为经代理的 DoH，再在原故障环境复测 |
| UDP 路径 | 前次同一网络下，原始 STUN 和 SOCKS UDP 探测都没有收到有效回复 | 单独核对节点及整条代理链对 UDP 的支持；更改 DNS 不等于修复 UDP |
| 验证环境 | 非 TUN / 另一节点上测通，不能证明固定出口 + TUN 也正常 | 分开记录两种状态；只在目标状态验收修复 |

这些是不同层面的问题，不是“每次都因为网速慢”。目前能定位到 DNS 和 UDP 路径不通，但无法仅凭超时确定是哪一台设备或服务丢弃了请求。之前反复改文案、延时，以及在不同网络条件下获得成功结果，没有完成同一故障环境的端到端验收。

## 30 秒到底如何计算

两项同时开始，各自总预算约 30 秒，不是串行等待 60 秒，也不是每一步都等 30 秒。获得完整结果或系统已经返回错误时会提前结束。

- DNS：会话 HTTPS 最多 10 秒；系统查询使用剩余预算，预留 4 秒用于报告及收尾；报告请求还受总截止时间约束。
- WebRTC：备用名称查询最多 5 秒；Edge 启动、页面加载和 ICE 共享剩余预算，JS 截止时间不会晚于浏览器调试通道的取消时间，预留回传时间。
- 界面到约 30 秒仍未取得完整结果就停止等待、显示黄色并清理后台任务；清理可能稍后完成。
- “Windows 返回 1460”表示系统查询自己超时；“程序达到等待上限时仍未返回”表示工具停止等待。二者分别计数。
- 页面顶部“必要检查耗时”与两项后台检测的耗时不同。

如果网络根本不转发该协议，继续把等待改成几分钟也不保证能成功。

## 需要用户手动处理的网络项

本版不会替你修改网络。若现有设置仍为 tcp://8.8.8.8，建议只在 v2rayN 的 **TUN / sing-box 远端 DNS** 对应设置中：

1. 记下原值，将远端地址改为 `https://dns.google/dns-query`。
2. 保持它使用代理出站，保留原节点、固定出口及其他路由设置；不修改 Windows 网卡 DNS。
3. 在 v2rayN 中保存设置、应用或重启代理核心。只编辑自动生成的 configPre.json 可能在下次启动被覆盖，因此应修改持久化设置。
4. 切回目标固定出口并开启 TUN，运行本工具的“检测 DNS / WebRTC”，最长等约 30 秒。不需要在切换期间与助手保持连接；可以完成后切回工作网络再反馈截图。

标准 DoH 的路径是 /dns-query，不是浏览器查看页面，也不是 JSON 查询 API 的 /resolve。若所用 v2rayN 版本没有对应字段或保存报错，保留原值再核对该版本设置，不直接覆盖整份配置。

DNS 验收：本轮取得有效解析器报告；失败时查看具体系统错误码与阶段。WebRTC 验收：两处 STUN 取得有效公网反射地址；无回复仍为黄色，不因修改 DoH 自动算通过。若只需在 UDP 被限制的环境中使用工具，可保留该提醒，无需为了得到绿色而打开不受控 UDP 或放宽固定出口。

## 仍可能遇到的情况

- 第三方报告服务故障、限流、超时或改格式：仍会黄色；不自动改用指定公共 DNS 冒充 Windows 路径。
- DNS 服务器出口池轮换：会提示基线变化，不据此认定真实 IP 泄露；可选基线可留空。
- 独立 Edge 无法启动或本机调试通道失败：会显示失败阶段，不再笼统归因于 STUN 没回复。
- 切换节点或 TUN 后，旧报告仍只代表旧网络。再次点击检测获取新结果；观察模块不会持续跟踪所有网络变化。
- 新版代码的离线验证不等于目标节点的实时验收。当前版本未验证网络设置修改后的结果。

依据：[Google 标准 DoH](https://developers.google.com/speed/public-dns/docs/doh)、[Windows 1460 错误定义](https://learn.microsoft.com/en-us/windows/win32/debug/system-error-codes--1300-1699-) 和 [WebRTC ICE 错误规范](https://www.w3.org/TR/webrtc/#rtcpeerconnectioniceerrorevent)。
